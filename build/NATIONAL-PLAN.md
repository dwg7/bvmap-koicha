## 3. ストレージの見積もり(必要な空き)

**案 A(セルごとに作り、そのまま置く)**: 取得したファイル 16.9GB を残し、セルを 1 つずつ作って、変換後に中間の mbtiles を消す。
- 東日本を作る時点のピーク: 16.9(取得物)+ 12.5(mbtiles)+ 11.5(PMTiles)+ 3.2(北海道)≒ **44GB**
- 西日本を作る時点のピーク: 16.9 + 8 + 7.3 + 3.2 + 11.5(東日本)≒ **47GB**
- 余裕を 2 割とって約 **55GB**。最終的に残るのは、出力の約 21GB(取得物を消せばそれだけ)。

**案 B(最後に 1 本に結合する)**: 案 A の上に、`pmtiles merge`(1.28.0 にある)で 1 本にする(約 21GB を追加で書く)。
- ピーク: 16.9 + 21.5(セル)+ 21.5(結合物)≒ **60GB**。余裕を含めて約 **75GB**。

**この Mac の空きは 12GB(全体 460GB のうち 97% 使用)なので、足りない。** 外付けの SSD か、大容量の環境が要る。**余裕を見て、空き 150GB 以上を推奨**
(再実行・取得物の保存・結合物・バックアップのため)。メモリは 8GB で足りる(下記)が、16GB 以上あると安心。

**メモリの注意**: 各ワーカーは、セルの索引(`PMTilesIndex`)を持つ。東日本は約 127 万エントリで、北海道(78 万)の約 1.6 倍。
fork の後で参照カウントのために共有が崩れていくので、ワーカーあたり 500MB 前後を見込む。8GB の Mac では `--workers 5` が安全。
(D32 のリークは直したが、増えた場合に備えて、各ワーカーのメモリを定期的に記録する。)

## 4. 実行環境の候補

| 候補 | 利点 | 注意 |
|---|---|---|
| この Mac + 外付け SSD(500GB 以上、USB 3.1 NVMe) | 追加の設定が要らない。8 コアで、計算は約 2 時間。 | SSD の用意。メモリ 8GB なので、ワーカー数を絞る。 |
| クラウドの VM(例: 8〜16 vCPU、メモリ 32GB、NVMe 200GB) | 回線が速い(取得が速い)。メモリに余裕。数時間だけ借りる。 | 費用(数ドル程度)。stars への転送の下りがある。VM に認証情報を置かない(データは公開物)。 |
| stars のサーバー | ディスクは 1.3TB 空き。転送が不要。 | 本番のサーバー(Raspberry Pi 系と聞いている)で、ビルドの負荷をかけるべきでない。**不可。** |

どの環境でも、手順は同じ(`build/build.sh` と本書)。

## 5. 手順(ゲート付き)

**0. 準備**
- 空き 150GB 以上、`pmtiles` 1.28.0、`mlt` 0.4.3(sha256 を `tools/` で照合)、`python3 -I`、電源接続、`caffeinate -i`。
- **再開できるビルドにする(実装が要る)**: `build_koicha.py` に `--resume` を足す(既存の mbtiles のタイルを読み、作り済みのジョブを飛ばす。5 万タイルごとのコミットで、止めても壊れない)。
  いまは、止めると最初からやり直しになる(今回の北海道で実際に起きた)。**実装して、東京・北海道の一部で、止める→再開→出力が一致、を確かめてから始める。**
- ビルドは、`os.setsid()` で独立したプロセスにして、ログを `data/koicha/` に書く(D32)。

**1. bvmap 全体の取得(hfu さんの許可が要る)**
- `curl -C - --retry`(単一ストリーム、再開可能)で、16.9GB を 1 本で取る。約 32 分。並列にしない(地理院への負荷を増やさない)。
- 取得前後で、`Content-Length`(16,900,763,181)・`ETag`・`Last-Modified` が一致することを確認し、取得物の sha256 を `provenance.txt` に記録する。
  **取得中・ビルド中にファイルが更新されたら、中止してやり直す**(ETag が変わる)。
- D5 の守りの代わりに: 取得前に必ず HEAD でサイズと ETag を確認し、サイズが想定(16.9GB)と違えば取得しない。

**2. セルの確定(ローカルで、地理院に触れない)**
- 取得物の z4 のタイルを列挙して、実際にデータのあるセルを確定する(`4/14/5`、`4/14/6`、`4/13/6`、小さなセルが本当にあるか)。
  `--dry-run` の 6 セルのうち、小さな 3 つは、隣のセルの縁を含んでいる可能性がある(確認する)。小さなセルは、1 つの小さなファイルにまとめるか、東日本・西日本へ寄せるかを決める。

**3. セルごとのビルド**(北海道は作成済み。**東日本 → 西日本 → 小さなセル** の順。東日本は東京を含み、最も重い。ここで時間とメモリの実測を取る)
- `build_koicha.py <名前> --cell <z/x/y> --source data/bvmap/optimal_bvmap-v1.pmtiles --roads --seams`(取得物を、そのままソースにする。セルごとの抽出ファイルは作らない)。
- 変換: `mlt convert --verify` → `pmtiles edit --metadata`(D16)。変換後に mbtiles を消す。
- **各セルのゲート(全部通るまで次へ進まない)**:
  1. タイル数 = 期待値(ソースのキーから数えた親タイルの数)。
  2. `mlt convert --verify` が通る。
  3. `stats_pmtiles.py`: 最大タイル ≤ 512KB(D19)、目安 256KB 超の枚数を記録。
  4. `check_seams.py`(z15・z13・z10 で 70 束以上): 面積・線長が理想値の 1.0000±1e-4、`props only in new: 0`。
  5. 目視 6 か所以上(市街地 2、山間 1、島 1、海岸 1、セルの縁 1)。旧(従来方式)との左右比較。
  6. ローカルの Martin 1.14.0 で配信し、TileJSON とタイルを取得する(複合ソースを含む)。
  7. sha256 とサイズを記録する(`provenance.txt`)。

**4. z3 の概観(小さなビルド)**
- セルのビルドは z4 から(`minzoom` = セルの z)。bvmap の z4(全国で数枚)を、koicha の z3 として束ねる小さなビルドを足す(`build_koicha.py` に `--maxzoom` を足す)。いまの東京版には、z3 の 1 枚がある。

**5. 結合(案 B の場合)**
- `pmtiles merge`(1.28.0)で、セルのファイルを 1 本にする。検証: タイル数の和が一致、`vector_layers` の和集合、`bounds`、`minzoom`/`maxzoom`、MLT のタイルが無傷(元のセルのタイルとバイト単位で一致)。
- **ローカルの Martin 1.14.0 で、結合物を配信して確かめる**(MLT、約 21GB のファイル)。stars のサーバーの Martin の再起動時間・メモリは、stars 側に確認する(下記)。

**6. stars への配置(hfu さんの確認が要る。stars のセッションが起動している必要がある)**
- D21・D29 と同じ手順: `.new` で転送 → sha256 照合 → `mv` で入れ替え(Martin は再起動不要)。**新しい名前のファイルとして置く**ので、既存の北海道・東京は触らない。
- 転送は再開できる方法(`rsync --partial`)。21GB の所要時間は回線次第(上り 10MB/s で約 35 分、1MB/s なら約 6 時間。**回線の実測を先に取る**)。
- stars の確認事項(stars セッションが起動したら尋ねる): CPU・メモリ・空き、Martin のメモリと起動時間、20〜25GB の PMTiles を載せる際の懸念、バックアップ容量。
  (11/21 に尋ねようとしたが、stars のセッションが起動していなかった。)

**7. 切り替えと移行期間**
- スタイルの `sources.bvmap.url` を、新しいソースに切り替える hfu/stars の PR(既存ファイルの編集。再起動不要)。
  **切り替えの途中で、同じタイルが 2 つのソースに重ならない**ようにする(複合ソースで、重なるタイルの扱いは未検証。D20)。新しいソース 1 つ(または新しいセル群だけ)に切り替える。
- 移行期間(案: 2〜4 週間)は、古い北海道・東京を残す。テストページで、旧 URL を使う利用者がいないことを確認する。
- 移行期間のあと、`bvmap-koicha-hokkaido` と `bvmap-koicha-tokyo` を削除する(**そのつど hfu さんの確認。元に戻せない**)。
- テストページ(`docs/index.html`)の範囲判定・ボタン、README の数字、`CLAUDE.md` を更新する。

**8. ロールバック**
- 切り替えは、スタイルの PR の差し戻しで戻せる(古いファイルが残っている間)。
- 配置は、新しい名前のファイルなので、削除すれば元に戻る。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 途中でディスクが満杯になる | 開始前に空きを確認(150GB 以上)。変換後に mbtiles を消す。ビルド中に残りを監視。 |
| 途中で止まる(セッション終了・再起動・スリープ) | `--resume`(実装が要る)。独立プロセス。`caffeinate`。 |
| ビルドの途中で地理院のファイルが更新される | 取得前後の ETag を照合。更新されたら、全体をやり直す(別の版を混ぜない)。 |
| メモリ不足(東日本の索引が大きい) | ワーカー数を絞る(5)。メモリを記録。16GB 以上の環境が望ましい。 |
| 東京・大阪などで、タイルが上限(512KB)を超える | 実測で、東京の最悪は 113.7KB、5 範囲の最悪はそれ以下。余裕は大きい。ゲート 3 で全セルを確認。 |
| Martin が大きなファイルでメモリや起動時間を食う | ローカルで先に確認。stars に問い合わせる。 |
| 複合ソースで重なるタイルの扱いが不明 | 重ならない構成にする(切り替えを 1 回で)。 |
| 継ぎ目の処理(D31)の想定外 | ゲート 4・5。縁・島・海岸の目視。旧方式との比較。 |
| 取得物の破損 | サイズ・ETag・sha256。`mlt convert --verify`。 |

## 8. 決まったこと・残っていること(2026-11-21 時点)

**決まったこと(hfu さん)**
- **最終形は、1 本**の `bvmap-koicha`(案 B。セルごとに作り、`pmtiles merge` で結合する)。
- **移行期間は 3 週間**(古い北海道・東京を残し、3 週間後に削除する。削除は、そのとき hfu さんに確認する)。
- **実行環境は、来週の後半に、`slate`(いまはアクセスできない大容量の環境)で行う方向**。環境が使えるようになったら、第 3 節のストレージ・メモリの要件に照らして確かめる。
- **北海道版(`roads-seams`)は、stars に入れ替えてよい**(2026-11-21 に承認。D34)。

**残っていること**
1. **取得の許可**: bvmap 全体(約 16.9GB)を、単一ストリームで取ること(約 32 分)。`slate` での実行の直前に、改めて確認する。
2. **`slate` の仕様の確認**: 空きストレージ(150GB 以上が望ましい)、メモリ、CPU コア数、地理院・stars への回線。分かったら、第 3・6 節の数字を直す。
3. **取得物の扱い**: ビルド後に残すか(再現性)、消すか(約 17GB の節約)。
4. **実装(`slate` に移る前に、この Mac で済ませる)**: `--resume`、z3 の概観ビルド(`--maxzoom`)、結合後の検証スクリプト。
5. **stars への問い合わせ**: CPU・メモリ・空き、Martin のメモリ・起動時間、約 21GB の PMTiles を載せる際の懸念。
