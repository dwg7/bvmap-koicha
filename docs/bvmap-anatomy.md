# bvmap タイルの中身

`chashaku/anatomy.py` が、bvmap の z13〜z16 の 2,753 タイル(5範囲、`chashaku/areas.tsv`)と、東京中心の z4〜z12 の単一タイル9枚を数えた結果。
元の CSV は `chashaku/results/anatomy_*.csv`。最初のプロンプトで「まだ確かめていないこと」とされた三点(BldA のズーム範囲、
`vt_flag17` の分布、tile extent)への答えは、先頭にまとめる。

- **データ**: `optimal_bvmap-v1.pmtiles`、`Last-Modified: 2026-09-17`、データは 2026年7月1日時点(README)。取得 2026-10-12(`chashaku/results/provenance.txt`)。
- **生成**: PMTiles のメタデータの `generator_options` によれば tippecanoe(`-pf -pk -S 2`、z4〜7 は `-d 14 -D 14 -m 14`)で、
  z4〜7 / 8〜10 / 11〜13 / 14〜16 の4つの mbtiles を tile-join で束ねたもの(名前は 5000k, 1000k, 200k, 25k)。
  PMTiles の内部・タイルとも gzip。**タイルの gzip は `gzip -9` と同じ大きさで、再圧縮するとバイト数が全 2,753 タイルで一致した。**

## 三つの答え

### 1. 建築物(BldA)は z14 から入る。z15 は z16 の 1/20 以下しかない

- z4〜z12(東京中心の1枚ずつ)にも、z13(5範囲のどのタイルにも)にも **BldA はない**。z14 から現れる(25k 層の開始と一致)。
  サンプルは5範囲と東京1地点なので、「全国で z14 から」は未確認(ただし最も密な範囲でも z13 には無かった)。
- `vt_flag17` で切り替えられていない(BldA には `vt_flag17` キー自体がない)。z16 のタイルの BldA は、z16 と z17 で同じ建築物。
- **件数は z16 で跳ね上がる**(同じ範囲の地物数の合計):

| 範囲 | z14 | z15 | z16 | z16 / z15 |
|---|---|---|---|---|
| tokyo | 2,399 | 4,795 | 94,972 | ×20 |
| osaka | 1,952 | 4,674 | 117,292 | ×25 |
| sapporo | 886 | 2,125 | 49,853 | ×23 |
| obihiro-rural | 741 | 1,750 | 125,110 | ×71 |
| taisetsu | 4 | 7 | 27 | ×4 |

  z15 の建築物は、都市部で z16 の 1/20〜1/25、帯広郊外で 1/71 しかない。これが「スカスカ」の正体で、
  このプロジェクトが埋めようとしている隙間そのもの。(taisetsu は建築物がほとんどない。)
  なお地物数は、タイルの縁(buffer)で重複した分を含む。z16 のほうが縁が多いので、比は少し大きめに出ている。
- 建築物1棟あたり平均 約5.8 頂点(z16、tokyo: 546,456 頂点 / 94,972 地物)。

### 2. `vt_flag17` の分布

- **キーがあるのは5層だけ**(Anno, RailCL, RdCL, TpgphArea, WStrL)で、**z16 のタイルにしかない**。z13〜z15 のタイルには存在しない。
- キーがある層では、**全地物にキーがある**(z16 で「キーが無い地物」は0件)。「なし」と「0」の区別は、z16 では問題にならない。
- **値 2 が現れるのは Anno と WStrL だけ**。RdCL、RailCL、TpgphArea には、サンプルでは値 2 が1件もなかった。
  つまり z17 以上では、道路中心線は、z16 までの地物(値 0、ほとんど全部)が消え、値 1 のごく一部だけが残る
  (代わりに RdEdg, RdCompt が描かれる、とスタイルから読める。描画での確認はしていない)。

### 3. tile extent

- **z8〜z16 は 4096、z4〜z7 は 16384**。MVT の version は 2。z13〜z16 の 21,587 層インスタンスすべてで 4096。
- 4096 のタイル4枚を束ねるときは 8192 にすれば、座標の精度を落とさずに束ねられる(`hyp` と `contra` の z13〜z15 で実際にそうしている)。
  MLT 側でも extent 8192 のタイルは問題なく符号化でき、`mlt convert --verify` が全件成功した。

読みどころ:

- **RdCL(道路中心線)は z13 から**、z14〜z15 のタイルの中身の 7〜8 割(都市)を占める。z16 では RdEdg が加わって 2〜3 割に下がる(生バイト、`chashaku/results/anatomy_layers.csv`)。
- **Cntr(等高線)と TpgphLine は山地・郊外で重い**(taisetsu の z14 で Cntr が 90%)。TpgphLine は z14 では 1,829 地物だが、

- **RdEdg 87,992、RdCompt 6,230、RailTrCL 6,396 は z16 だけ**(z17 専用層)。z17 専用の4層を `hyp` の z15 で捨てると、その分が軽くなる。

## 属性の種類と大きさの目安

z16 の5範囲合計。`tag(B)` は地物ごとの tag 配列(キー番号+値番号の varint)の生バイト数、`value表(B)` は値テーブルの生バイト数で、
どちらも**圧縮前**。MLT や gzip ではかなり小さくなる(tag の繰り返しは辞書や差分で消える)ので、占有率は上限の目安。

## 限界

- 5範囲 + 東京1地点のサンプル。全国の分布は未確認。
- `vt_flag17` の意味(0, 1, 2)は readme とスタイルの記述に従った。値 2 が RdCL にないことの理由(データがないのか、z17 以上では道路中心線をほぼ描かない設計なのか)は確かめていない。
- スタイルの `minzoom` は、`std.json`(gsi-cyberjapan/optimal_bvmap の main、2026-10-12 取得)で確認した。
