# chashaku 計測レポート(第1版)

dwg7 の活動であり、国土地理院の公式な製品ではありません。bvmap の中身は [docs/bvmap-anatomy.md](../docs/bvmap-anatomy.md)、
決めたことと理由は [DECISIONS.md](../DECISIONS.md)(D3 計測設計、D4 エンコーダー、D5 取得事故、D6 提案)。

## 要約

**maxzoom は 16 がよい。** 間引きは、タイルの大きさの面では**今は要らない**。

1. **maxzoom 16(`hyp`)と 15(`contra`)の比較。**
   - 同じ土地を覆うのに要する量は `contra` のほうが多い。表示 z15 で `hyp` の 1.23〜1.31 倍、表示 z16 で 1.07〜1.12 倍
     (都市・郊外の4範囲。山地 taisetsu は 1.00 倍と 0.96 倍で差がない)。z17 の内容まで入った一番重いタイルを、z15 表示でも読むため。
   - 最悪のタイルも `hyp` のほうが小さい(z15、MLT+gz、tokyo の最大 67.9KB 対 78.0KB)。
   - 代償は、アーカイブが `contra` の 1.66〜2.04 倍になること(z15 と z16 の両方に建築物が入る)と、z16 表示のときのタイル枚数が4倍になること。
   - 全体を決める最悪のタイルは、どちらでも z13(下記)で、maxzoom の選択とは無関係。
2. **間引きの要否。**
   - 最悪のタイルでも MLT+gz で 104.8KB(tokyo 13/7276/3225、MVT+gz では 138.8KB)。5範囲で 100KB を超えるのはこの1枚だけ。
     80KB を超える 10枚もすべて z13(山地の等高線と都市の道路)。
   - 大きさの目標値(上限)が決まれば、判断は数値でできる。**目標値を教えてください**(D6 の保留事項)。
   - 目標を設けるなら効きそうなのは、z13・z14 の道路中心線 RdCL(都市で 49〜66%)と、山地の等高線 Cntr(69〜92%)。
     建築物は z15 で 71〜78% を占めるが、これは増やしたいものなので、間引き候補にしない。

補足の三点:

- **MLT だけでは、一段ずらした分を取り戻せない。** MLT+gz は MVT+gz の 0.73〜0.96 倍(都市部は 0.73〜0.85 倍)で、15〜27% 小さい。
  一方、一段ずらすと、都市の z13 と z15 のタイルは同じ表示ズームの bvmap の 2.7〜3.7 倍になる(z14 は 1.3〜1.6 倍、z16 は 0.67〜0.85 倍)。
  最初のプロンプトの見込みどおり、正味でタイルは大きくなる。ただし絶対値は小さい(都市部の中央値で 11〜86KB)。
- **z13 が山場。** `hyp` の z13 は、bvmap z14 で入る 25k 層(等高線、道路の全量など)を4枚束ねる。山地では bvmap の z13 が 3KB、
  `hyp` の z13 が 83KB(×28)、郊外(帯広)で ×6 になる。地図が「濃くなる」代わりに、z12 から z13 への切り替わりで急に重くなる。
- **束ね方の検証は通っている。** bvmap 2,753枚はバイト単位で再現でき、束ねた後の地物数・頂点数は子の合計と一致し、
  MLT は全 6,266枚が `--verify` で復号一致した(`validate.py`、`mlt_convert.log`)。ただし**描画での確認はしていない**
  (後に D7 で確認済み)。

## 条件と出所

- 素材: `optimal_bvmap-v1.pmtiles`(`Last-Modified: 2026-09-17`、データは **2026年7月1日時点**)。取得 **2026-10-12**(UTC 10:36)。`results/provenance.txt`。
- 範囲: tokyo, osaka, sapporo, obihiro-rural, taisetsu(`areas.tsv`)。bvmap の z13〜z16、計 2,753枚。取得はすべて `pmtiles extract --bbox`(約 24MB)。
  最初の取得で全国分を約10GB 取ってしまった事故があった(D5)。
- ツール: `mlt` 0.4.3(maplibre-tile-spec 公式リリース `rust-mlt-v0.4.3`)、`pmtiles` 1.28.0、Python 3.9.6(標準ライブラリのみ)、macOS arm64。
- 組み方: `bvmap`(基準)、`hyp`(仮説)、`contra`(対立案)。定義は D3。サイズは MVT+gzip -9、MLT のみ、MLT+gzip -9。
  gzip -9 は bvmap の保存サイズと全タイルで一致する。
- 統計: 中央値、95パーセンタイル(nearest-rank)、最大値。**complete**(子が全部そろったタイル)のみ。全タイル版は `results/summary.csv`。

- **z13・z14 は道路中心線 RdCL が主役**(都市で 49〜66%)。z13 は bvmap の z14(25k 層)を束ねたもので、道路の全量が入っている。
  帯広郊外は RdCL 38% に等高線 Cntr 18〜25% と注記が続く。
- **山地(taisetsu)は等高線 Cntr が 69〜92%**、z15 以降は TpgphLine が約 2 割。
- **z15 は建築物 BldA が 71〜78%**(都市)、z16 は 61〜68% と、道路縁 RdEdg が約 2 割。
- 目安の計算: tokyo の z13 の最悪タイル(104.8KB)を 80KB(−24%)にするには、RdCL(z13 の平均で 58%)だけを減らすなら RdCL の約 4 割を減らす計算になる。
  ここは層の平均の割合から出した粗い見積もりで、実際の効果は間引きの方法に依る。

## 限界

- 5範囲 + 同じ bbox での測定。全国の最悪値、特に最も密な市街地は未測定。
- complete タイルの数は z13 で少ない(都市部 1〜2枚、郊外・山地 12枚)。中央値や p95 は傾向として読むこと。最大値は全タイルの最大(`max_tile` 列)。
- 子タイルの buffer は切り落とさず束ねた。縁の重複が残っているので、サイズは悲観側(重め)に出ている。
- 描画の確認は、tokyo の東京駅周辺を MapLibre GL JS 6.14.0 で目視しただけ(D7)。extent 8192 の MLT と z14〜z16 の層構成は問題なかった。
  他のクライアントと描画性能は未確認。
- MLT のエンコーダーは開発が速く、版が変わるとサイズが変わる(0.4.3 を使用)。`--fields` による属性の型指定など、
  サイズに効きうるオプションは試していない(D4 の保留事項)。
- 地物は触っていない(束ねる・捨てる・エンコーディングだけ)。属性の整理や総描は、この結果を見てから決める。
